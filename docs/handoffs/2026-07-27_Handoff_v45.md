## The finding: a documented trap that one tool never got

The game reads one-shot inputs (accept, talk, buy, dismiss, travel) with
`JustDown`, and Phaser clears the pending flag on keyup, so **a zero-gap down+up
landing between two starved frames is silently lost**. `page.keyboard.press()`
is exactly that shape.

`tests/e2e/drive.ts:11-14` documents this precisely and has carried `tapKey` for
it since. Autoplay used raw `press()` for **all sixteen** of its one-shot inputs
and never got the fix.

That explains the reported symptom exactly. The old driver pressed board slot 1
once per loop iteration and verified nothing, relying on a press eventually
landing on a live frame. Sometimes eleven attempts; sometimes the whole 220-step
budget, which is the run #440 captured. Saltmere and the board were both
innocent.

The fix ports `tapKey` (hold until the frame counter advances), adds an
`acceptSlot` that verifies both halves of the board's arm-then-confirm (#321),
and works down the board skipping a slot that will not take.

**New autoplay baseline, worth keeping:**

Every settlement in all four regions reconnected, including Saltmere and

## Two lessons, both about mistaking a partial signal for a result

### A fix that removes the symptom can leave the tool worse

The change landed in two stages, and the intermediate state is the instructive
one. With the skip logic but **without** `tapKey`, the driver stopped stalling
and walked the entire ring, and delivered **nothing**: every accept still failed
and was now abandoned rather than retried.

That state would have closed #440 as written. The log looked healthier than
before. It was a strictly worse tool, trading "stalls but delivers" for "never
stalls but never delivers". **The skip path is only safe once presses are
reliable**, which is why it fires zero times in the final run. A safety net that
fires is a bug report, not a feature.

### A screenshot is a point in time, not a result

Three follow-ups were flagged after the #440 fix. **Two were wrong, and both for
the same reason.** Recorded so nobody re-investigates:

- *"The wagon read 25/97 despite `?nowear`."* Wrong. `maxConditionForLevel` is
  `25 + (level - 1) * 9`, so a level-9 courier has a 97-point tank, and the
  current value sits at its starting 25 because nothing wore it and nothing
  repaired it. A growing denominator misread as a shrinking numerator. `nowear`
  is correct.
- *"Ashmoor's ford was never opened."* Wrong as stated, and became #444. The
  claim came from reading `summary-ashmoor.png` as an end-of-run state when it
  is a snapshot taken mid-run, at the moment the region clears.

Both were resolvable from evidence already in hand when they were raised. Filing
them as written would have put two non-defects into the tracker, which is the
trap 2 failure. **Check a flag against the code before filing it, not after.**

## #444, and why a cosmetic bug was worth fixing

The ford trip was the last thing done in a region, after the final delivery had
already cleared it. The cleared panel appears on that delivery and the driver
screenshots it on the same frame, so every `summary-<region>.png` read "Ford
shortcut: not opened" on runs that opened the ford seconds later.

No gameplay was wrong and no test was affected. But the screenshots are the
tool's headline artifact, so its most visible output described a run that did not
happen. That is trap 5 in a different medium, and it had already produced one
false lead in this session.

Fixed by moving the signpost trip to the front of the home routine, so the claim
becomes true rather than the artifact being re-photographed. Side benefit: the
ford is now open *during* each region's deliveries, so autoplay's routing
exercises it for the first time.

Verified by reading the screenshots, not the log: a log line moving earlier would
only prove the code was reordered.
