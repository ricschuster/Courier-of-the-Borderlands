## What changed and why

### The arc guard failed on `main`, and the cause was not the diff

Run 31314702542 failed at the 12m cap, its retry failed again with
`courier stuck at (4,18) heading for (2,8)` (Ironhollow heading for Greywater),
and a manual dispatch of the same commit on a fresh runner passed first try in
7.3m. Three samples, one conclusion: load, not code. `vite` 8.1.4 was the
plausible suspect and is exonerated.

**A Playwright retry is not a second sample.** It reruns on the same runner, so
it inherits the load that caused the failure. Two attempts failing back to back
is close to one observation, not two. The independent third sample is what
settled this, and reasoning from the first two nearly sent the session into
reverting a clean dependency bump.

### The budget was an absolute where it needed to be a ratio

| | Jul 11 (#107) | 08-09 | Change |
|---|---|---|---|
| Passing arc duration | 4m02s | 7.3m | +81% |
| `test.setTimeout` | 480_000 | 720_000 | +50% |
| Headroom | 2.0x | 1.64x | worse |

Fenmarch, Saltreach and Ashmoor each added drive time. The cap was raised once,
by less than the arc grew, so load that used to be survivable now pushed a 7.3m
run past 12m. Passing runs have been stable at 6.3-7.6m for ten days, so this is
a margin problem and not a creep still in progress. 1_080_000 puts it back at
2.5x, and the comment now states the rule as a ratio with an explicit revisit
trigger (clean time past ~7.2m).

The retry also went, because it cannot rescue a load failure and doubles the
cost of a real one. Worst case drops from ~25m to 18m.

Post-merge arc: **7.5m, passed, first attempt.**

### Turbo was considered and rejected

#107's own next-steps suggest raising the arc's turbo multiplier. That is not
safe. `src/scenes/map-scene-e2e.ts:279-290` holds turbo at 2x because, against
the e2e frame clamp in `main.ts` (`fps: { min: 20 }`, 50ms max per frame), 2x
tops out just under one tile of movement per frame, and every exact-tile
interaction gate depends on that. 3x would break those gates precisely in the
starved-frame case the flake lives in. Raising `fps.min` alongside restores the
bound but cancels the wall-clock gain under starvation, because the clamp then
advances game time proportionally slower. The lever only pays on healthy runners.
Recorded in #107 so it is not re-proposed.

### #448 was closed by its own PR body

PR #450 said "so this does NOT close #448 and the issue stays open". GitHub's
closing-keyword parser matches `close #448` and does not understand negation, so
the sentence written to keep the issue open is what closed it. v47 states the
issue stays open; the tracker disagreed, and this is why.

**Use `Refs #N` when not closing.** Any form of close/fixes/resolves adjacent to
the number will close the issue regardless of the surrounding words.

### The arc's "three regions" comment is about the capstone, not the route

Checked because Ashmoor landed in #438 after that comment was written.
`dialogue-content.ts:81-84` gates `blockade_broken` behind
`FLAG_SALTREACH_METHOD` and `FLAG_FENMARCH_COST`, so the capstone needs
Greybridge, Saltreach and Fenmarch only, and Ashmoor is not required.

The driver still goes there, though. It walks gateways to any region it has not
exhausted, and the measure run below reports per-region wear for **four**
regions including Ashmoor. So "three regions" is right about what the arc
*proves* and understates what it *drives*. Not worth a change on its own, but do
not read that comment as a statement of route length.

No coverage gap either way: `ashmoor-ring.spec.ts` asserts Ashmoor's two-door
topology directly and runs in the `chromium` project on every PR.

### #448: Demanding is slow, not wedged

v47 left one question standing, and it is now answered. Re-run locally with a 5x
budget (`--timeout=3600000`):

```
=== TRAVEL-SINK MEASUREMENT (demanding difficulty, wear ON) ===
completed: capstone=true deliveries=9
final: coins=1 wagon=12 totalWear=24.7
strand events (condition hit 0): 12
condition distribution over 100 samples:
  =0: 16   1-25: 50   26-50: 22   51-75: 12   76+: 0
1 passed (9.9m)
```

**The Demanding arc completes.** It reaches the capstone. It was never
soft-locked, so the revised diagnosis in #448 (a scripted driver with no "come
back later" behaviour walking into legs it cannot survive) is not what stops the
run.

What stops the run is the same thing that stopped the arc guard: a budget that
did not grow with the content. `travel-sink-measure.spec.ts:156` still carries
`test.setTimeout(720_000)`. The run takes 9.8m on a machine that does the full
arc in 3.8m against CI's 7.3m, so CI is roughly 2x slower here, putting Demanding
around 20m. Against a 12m cap it can only ever time out.

This is #455's finding a second time, in a spec that did not get the fix.

The tuning signal is separate and is for the owner, not for a fix: 12 strand
events, half of all samples in the 1-25 condition band, never once above 75, and
one coin left at the end. That is a punishing run that a player can finish, which
may be exactly right given the owner's direction on teeth.
